# 评测数据自检 Checklist

给测试分析工具造"带标准答案的卷子"时，逐项过一遍。每条都是本轮闭环回归
（60 例、含 23 条贴边界/对抗样本，生成器 0.2.1）实际踩过或守住的结论，
不是泛泛而谈。

## 一、真值可信度（先查这个，不过关后面全白做）

- [ ] **真值不是"注入了什么"**。若真值记录的是生成参数（"我在 5.0 秒注入了
      3 秒急刹"），而工具按同一套口径检测——两边共享假设，检出率 100% 只证明
      代码没写岔，不证明任何事。**真值必须由一份独立实现从数据里算出来。**
- [ ] **参考实现只照抄口径常量，不共用代码**。与工具同源的工具函数不算独立；
      两个实现一致才是"双方对口径理解一致"的证据。
- [ ] **回归时逐条比对两边的事件集**，不是只比总数。总数相等但区间错位
      （比如一边 [4.9,5.9] 一边 [5.0,6.0]）是边界语义分歧，比漏检更危险。
- [ ] **诚实声明数据等级**。生成的是公式合成的运动学级序列（时间-速度），
      就在 source.json 里写明，不冒充道路采集、不冒充闭环仿真。评测结论的
      适用范围随之声明：运动学口径成立，不代表真实噪声结构下成立。

## 二、对抗样本：参数范围按"结论必须成立"反推

造贴边界样本时，**先写死这条样本要证明什么，再反推参数上限**，而不是先随便
选范围再看结果：

- [ ] **"应无事件"的样本**，参数上界乘以最坏取整后仍够不到门槛。
      例：短急减样本要证明"下降间隔不够 4 个"，dip 上限取 0.34 秒——
      因为 0.35 抖出来会被取整圆成 0.4，样本悄悄变成"应有事件"的另一类，
      结论直接泄露。
- [ ] **"应有事件"的样本**，参数下界要留足余量。例：典型组减速度下限
      2.2 m/s²，保证 0.5 秒窗口降幅 ≥ 1.0 m/s 跨过门槛。
- [ ] **联合约束单独验**。单个参数合法不代表组合合法：末端车速至少保留
      3 m/s 余量，否则长时长 + 大减速度会造出"减速到停止"的非法场景。
- [ ] **每个模板配一条形状单测**，直接断言速度曲线在关键时间点的值，
      而不是只断言事件有无。形状错了，事件可能"碰巧"还对，但样本已经变质。
- [ ] **对抗组占足够比例**。混合批次里对抗组低于两成，边界情况基本跑不到；
      本轮配比：典型组六成、对抗组三成、负样本一成。

## 三、双层口径，分开读指标

工具的设计若是"宽筛 + 复核"（筛查门槛比事件口径宽），指标必须分两层，
混在一起读会得出错误结论：

- [ ] **检出率/误报率归宽筛层**。宽筛门槛更松，协议事件理应 100% 被候选
      覆盖——这个 100% 是可证明的，不是业绩。宽筛捞出无事件样本是设计使然，
      量化它（如本轮 19.6%）是为了说明固有成本，**不代表工具在真实数据上
      会误报**。
- [ ] **"口径误判"单独一类，且必须是 0**。定义：候选被工具自判"符合口径"
      （meets_numeric_rule），却没有真值事件支撑。**这才是实现 bug**；
      宽筛噪声（自判 below_numeric_rule）不是。
- [ ] **结构不一致单独一类**。有真值事件但候选簇数 ≠ 事件数 = 合并过头或
      切碎，检出率 100% 也掩盖了它。注意只在有事件的案例上计——
      负样本天然"1 候选 vs 0 事件"，算进去是指标虚高。
- [ ] **误报按两个口径分别报，且都不得冒充 FPR**。候选级（无支撑候选项 ÷ 总候选项）
      衡量复核工作量；簇级（无支撑簇 ÷ 总簇）衡量事件质量——接力/重叠候选在候选级
      会重复计数，簇级不会。两者分母都不是 FP+TN，**没有负例单位就不叫假阳性率**，
      命名里带"率"要格外小心。文档承诺与代码实现必须一致（曾经文档写按簇计、
      代码却按候选累计，靠外部评审的反例才抓到）。

## 四、工程细节（每条都实际咬过人）

- [ ] **时间参数对齐采样网格**。制动窗落在半个间隔上，"应有结论"没法手算
      复核，测试期望值全靠猜。
- [ ] **取整会改样本类别**。范围上限先想好取整方向：向下取整更保守，
      向上取整可能把样本推进另一类（见第二条短急减）。
- [ ] **查询条件类参数（如 --profiles 子集）不原地改全局配置**。同进程内
      跑第二批会继承上一批的配比，混进不该出现的模板，且不报错。
- [ ] **批次 ID 要带命名空间**。每批都从同一序号开始，第二批入库必撞 ID
      （同 ID 不同内容 → 全部失败），场景库没法跨批次积累。命名空间由配置
      （版本+种子+行数+配比）算短哈希：同配置可复现、不同配置可并存；
      刻意不含条数——多生成几条靠内容指纹去重，不该换一批新 ID。
- [ ] **哈希与抽样必须共用同一套排序口径**。命名空间按 `sorted(配比)` 算哈希，
      模板抽样却按 dict 原序遍历（= 命令行书写顺序）——同配比不同写法会算出
      同一批次名、抽出不同内容，入库必撞。修法是两处都按名字排序，并升生成器
      版本号让新代码换命名空间（版本号进哈希），不与历史批次混。
      测试见 `test_mix_writing_order_does_not_change_content`（逐字节比对）。
- [ ] **回归必须能拦错误版本**。只出报告不返回退出码的门禁等于没有：
      `--check` 把"导入完整性 / 口径误判 / 实现一致 / 漏检 / 确认漏检 /
      噪声容忍 / 结构一致"逐项判定，任一未过即非零退出，可直接挂 CI。
      噪声类指标只设容忍上限并允许调用方声明——把固有成本当成 bug 会天天红。
- [ ] **漏检要分两层：候选层与确认层**。候选覆盖正常而确认能力退化（区间收紧、
      匹配变严）时，只看候选层漏检会全绿放行。确认漏检 = 被候选覆盖但确认区间
      未覆盖的真值事件数，单独设门禁（默认 0）。测试见
      `test_confirmed_missed_independent_of_candidate_missed`。
- [ ] **困难案例要进固定回归集**。生成模式只能回答"工具对合成场景稳不稳"；
      采样缺口、人机分歧这类已知困难输入，用 `--cases/--labels` 对拍固化行为，
      阈值按**已知行为包线**设定（不是通过线）：跌破包线先人工评估是改进还是退化。
      人机分歧案例的阈值分歧本身就是记录在案的差异（seg_023：工具口径按缺口
      拆两个区间、人工判定连续事件），不要为了门禁全绿去改任何一边。
- [ ] **报告必须自带溯源四件套**：代码版本（git HEAD）、数据指纹（输入内容哈希）、
      阈值快照、逐项判定结果。四件套齐全，报告脱离命令行也能读；缺了任何一件，
      三个月后没人说得清这批数字是哪份代码对哪份数据跑出来的。
- [ ] **子进程显式传 UTF-8**。`-X utf8` 是命令行参数，不遗传给子进程；
      Windows 默认 cp936，中文输出按 GBK 打印、父进程按 utf-8 解码直接炸。
      测试里 `subprocess.run(..., env={**os.environ, "PYTHONUTF8": "1"})` 一行解决，
      且在"剥掉 PYTHONUTF8/PYTHONIOENCODING 的真实环境"下验证过才算修。
- [ ] **旧库打开要幂等补建新表并升版本号**（PRAGMA user_version 比大小，
      不是比是否为零）。加表不加迁移，老用户的库直接缺表。
- [ ] **导出物带 manifest**。下游拿一份清单（suite 元信息 + 逐场景真值 +
      指纹）即可对答案，不必解析每份 truth.json；指纹用于校验传输无损。

## 五、报告可读性

- [ ] **结论必须配"怎么读"**。100% 检出旁边必须写清它是可证明的、以及本轮
      真正守的是什么（如"口径误判 0 + 两边实现逐条一致"）。只报数字不写读法，
      看报告的人（包括三个月后的自己）会过度解读。
- [ ] **已知边界写进 README**，包括"参考实现不是第三方标准"这类诚实声明。
      面试被追问时，这份清单就是答题提纲。
- [ ] **生成器修复要连带处理历史数字**。修抽样顺序、修口径都会让同种子生成
      不同场景——README 里的基线数字必须用新代码重跑后更新，旧数字存入
      `generated/regress-wN/` 存档并注明生成器版本，不回溯改写。
